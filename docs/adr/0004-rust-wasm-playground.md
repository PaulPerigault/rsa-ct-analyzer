# ADR 0004: Rust and WebAssembly for the web playground

Status: proposed (2026-11-12). To be accepted or rejected before the first v0.2.0 issue starts.

## Context

A browser playground should analyse pasted certificates locally: no upload, nothing to install. The
analysis is written in Go. The same stack split as in the other projects applies: Go for CLIs and
services, Rust compiled to WebAssembly for reusable computation in the browser, static Astro for the
site (consuming `@paulperigault/design-system`). `design-system` already publishes two Rust crates as
WebAssembly packages, with a pinned toolchain and parity tests against its TypeScript code.

Compiling the Go code to WebAssembly (`GOOS=js`) is possible but ships a multi-megabyte runtime, which
conflicts with the zero-JavaScript-by-default budget of the site.

## Decision (proposed)

Write a `crates/rsa-core` Rust crate with the base checks (key size, small factor, perfect square, Fermat,
batch GCD), compile it to `wasm32-unknown-unknown`, and load it in an Astro island only after an explicit
user action. The Go CLI stays the reference implementation.

## Main risk: two implementations that drift

Two codebases implementing the same cryptographic checks will diverge unnoticed.

Mitigation, which is a condition of acceptance:

1. **Golden files** generated by the Go analysis from `testdata/` (a Taskfile target `data:golden`, to be added; fixed options): one
   JSON per sample, findings with ID, severity and evidence.
2. A Go test and a Rust test both read the goldens and fail on any difference.
3. CI regenerates the goldens and fails when they are stale, as the `data:check` target does for `testdata/`.
4. A finding added to one side without the other fails the build.
5. Property tests (`proptest`) compare batch GCD with the O(n²) definition in Rust, as `pkg/batchgcd` does
   in Go.

## Other consequences

- A second toolchain to pin (`rust-toolchain.toml`, `wasm32` target), audit (`cargo deny`, `cargo audit`)
  and keep updated.
- A size budget for the `.wasm`, measured before it is fixed.
- If the golden files cannot be kept in sync at reasonable cost, the fallback is a plain static site with
  recorded examples and no in-browser analysis.

## Alternatives considered

- Go compiled to WebAssembly: one implementation, but a large runtime.
- Server-side analysis: contradicts "nothing leaves the browser" and needs hosting.
- JavaScript reimplementation with `BigInt`: no better on drift, slower on large moduli.
